# OpenGraffiti 設計決定記録

作成日: 2026-08-31  
ステータス: 決定済み（実データPoCの合否だけを検証として残す）  
対象: `UD-001`～`UD-053`、`ISSUE-001`～`ISSUE-002`

## 1. 決定原則

- 2026年10月31日までの一人開発による発表用MVPを優先する。
- 実成果物を発表で使用し、配置はローカルを第一候補かつMVPの確定構成とする。
- 発表端末上で、静的Web、API、DB、作品画像を1台・1プロセス系に閉じ、会場回線を必須にしない。
- PLATEAUの原典CityGMLは変更せず、壁面対応情報、GLB内オーバーレイメッシュ、外部PNGおよび履歴を別管理する。
- 「適切に選択」は、機能の多さより、再現性、障害復旧、画面間の一致、期限内の成立性を優先して決める。
- PoC項目は方式を確定したうえで合否を実測する。実測不合格時だけ、記録した代替方式へ切り替える。

| 画面 | URL | 境界 |
|---|---|---|
| 3D都市 | `/areas/:areaId/city` | 独立ページ |
| 壁面詳細 | `/areas/:areaId/city/walls/:wallId` | URLを持つサイドパネル |
| 下地確認 | `/walls/:wallId/edit/source` | 独立ページ |
| 描画 | `/walls/:wallId/edit` | 独立ページ |
| 3Dプレビュー | `/walls/:wallId/edit/preview` | 描画ページ上の全画面モーダルルート |
| 公開確認 | `/walls/:wallId/edit/publish` | 描画ページ上のモーダルルート |
| 履歴 | `/walls/:wallId/history?revision=:no&at=:iso` | 独立ページ |

ブラウザ戻るは直前のURLへ戻す。都市のカメラ・選択壁・区画のパン/ズーム/選択時刻は`history.state`とメモリへ保持する。未保存の編集レイヤーはサーバー保存せず、同一タブ内の戻るだけ復元する。再読込・タブ終了・別URL直打ちでは編集を破棄するため、離脱確認を出す。

### UD-008 3D操作

- `MapControls`を使い、左ドラッグ=パン、右ドラッグ=回転、ホイール=ズーム、短い左クリック=Raycasterによる壁選択とする。移動量5px超は選択クリックにしない。
- 初期姿勢、注視点、最小/最大距離、方位範囲はエリアJSONへ保存する。対象範囲外へのパンは表示範囲を20%拡張した境界で制限する。
- 選択壁はシアンの2pxアウトライン、ピンアイコン、壁面名を併記する。選択可否は色だけで表現しない。
- 通常表示は元のPBR外観、受け入れ比較だけ`KHR_materials_unlit`相当の検証モードを使う。

### UD-009 静的スキーマ

- JSON Schema 2020-12、`schemaVersion = 1.0.0`。互換性のない変更はmajor、追加はminor、意味を変えない修正はpatchとする。
- ルートは`/assets/datasets/{datasetVersion}/`、ファイルは`manifest.json`、`areas/{areaId}.json`、`walls/{wallId}.json`、`sections/{sectionId}.json`、`canvases/{wallId}.base.png`、`canvases/{wallId}.mask.png`、`models/{areaId}.glb`とする。
- 全ファイルをmanifestのSHA-256とバイト数で検証し、URLへ`datasetVersion`を含めてimmutable配信する。

### UD-010 GLB生成

- PLATEAU GIS Converter v0.1.14、commit `e1c8feff7d8ff3e132230d6c21eaed4879e4a235`を固定し、LOD3の表示用glTFを生成する。
- 元ID・`WallSurface`・Appearance・2D基底の対応は専用前処理で生成し、Converterだけに依存しない。
- glTF Transform 4系でGLBへまとめ、`EXT_meshopt_compression`だけを適用する。Dracoと不可逆なテクスチャ再圧縮は使わない。
- 都市テクスチャの長辺上限は4096px、作品/基底/マスクは長辺2048px。GLB内の元テクスチャはPNG/JPEGのまま保持する。

## 5. 退色・画像・API・DB（UD-011～UD-017）

### UD-011～UD-013 退色とハッシュ

- 退色はサーバーだけが正規画像を生成する。各画面は同一のレンダーAPIとキャッシュを利用し、クライアントへ別実装を持たせない。
- 初版`rendererVersion`は`fade-rgba-v1`。時刻から`pPermille = clamp(floor((t - fadeStartAt) * 1000 / 15000ms), 0, 1000)`を求める。
- 入力A、壁面基底BはsRGB・非premultiplied RGBA8へ正規化し、マスク外のRGBAをすべて0にする。マスク内alphaは255とする。
- 差分輝度は`Y = round((77|dR| + 150|dG| + 29|dB|) / 256)`。3×3 Sobelの`min(255, |Gx| + |Gy|)`が48以上なら輪郭画素とする。
- 本書の`round(n/d)`は`sign(n) * floor((abs(n) + floor(d/2)) / d)`とし、負値を含めて0から遠い側へ0.5を丸める。言語組込みの丸め差へ依存しない。
- 色成分重みはp=0で1000、p=667で0となる線形値。輪郭重みはp=333で0、p=667で1000、p=1000で0となる三角形値。各画素の係数を`max(色成分重み, 輪郭画素×輪郭重み)`とし、`B + round((A-B)×係数/1000)`でRGBを求める。
- p=0はA、p=1000はBと画素一致する。段階は`0..332=鮮明`、`333..666=色あせ`、`667..999=輪郭のみ`、`1000=元の壁面`。
- `imageHash`は幅・高さを各4byte big-endianで連結し、上→下・左→右の正規化RGBA8を続けたバイト列のSHA-256小文字hexとする。alpha=0のRGBは0へ正規化する。PNGファイルバイトのSHA-256は`fileHash`として別記録する。

### UD-014～UD-016 転送・API・DB

- 公開は`multipart/form-data`をFastifyへ直接送る。10MBを上限とし、候補を`data/staging/{scenarioId}/{idempotencyKey}.png`へ保存、検証後に`data/artworks/sha256/{先頭2桁}/{imageHash}.png`へ同一ボリューム内で確定する。
- APIは`/api/v1`、JSON UTF-8 camelCase、OpenAPI 3.1。履歴上限21件のためMVPではページングしない。GETは`ETag: "state-{stateVersion}"`と`Cache-Control: private, no-cache`、ハッシュ付き静的資産は`public, max-age=31536000, immutable`。
- 主要APIは`GET /areas/:areaId/bootstrap`、`GET /walls/:wallId`、`POST /walls/:wallId/edit-context`、`GET /walls/:wallId/revisions`、`GET /sections`、`GET /sections/:sectionId/current`、`GET /sections/:sectionId/history?at=`、`GET /renders/:wallRevisionId?at=`、`POST /walls/:wallId/publications`、`GET /demo-scenarios/current`、`GET /events`、`POST /demo-scenarios/current/commands`、`POST /demo-scenarios/current/reset`。
- SQLiteのIDと時刻はTEXT、revision・stateVersion・bytes・permilleはINTEGER。外部キーON。公開は`BEGIN IMMEDIATE`で行い、`(scenarioId, wallId, revisionNo)`、`(scenarioId, wallId, sourceWallRevisionId)`、`(scenarioId, idempotencyKey)`へ一意制約を置く。
- `expectedWallRevision`はIDと版番号の両方を要求する。ロック待ちは5秒、`SQLITE_BUSY`は100ms、300ms、900msの最大3回まで再試行する。

### UD-017 文字列

- 表示名はNFKC正規化・trim後1～32 Unicode code point、作品タイトルは1～80 code point。
- 改行、C0/C1制御文字、双方向制御文字、空白のみを拒否する。日本語、英数字、一般記号、emojiは許可する。
- HTMLとして解釈せず、ログでは表示名・タイトルを記録しない。

| UD-038 | `PublicationAttempt`をArtworkと分離する。UUIDv4 idempotency key、scopeはscenario、requestHashを保存し、`PROCESSING/SUCCEEDED/FAILED`を持つ。同内容成功は同応答、別内容は409、処理中は409+`Retry-After: 1`。7日保持 |

| UD-040 | serverでも固定下地と正規化RGBAが完全一致する公開を拒否する。マスク内で1画素でもRGBAが異なれば描画ありとする。曖昧な面積閾値は置かない |

| UD-043 | PNGシグネチャ、IHDR、PLTE、IDAT、IEND、tRNS、sRGB、gAMA、cHRM、pHYsだけを受理し、未知のcritical chunk、APNGのacTL/fcTL/fdATを拒否。SharpでsRGB RGBA8・非premultipliedへデコード、ICC/metadataを除去、透明RGBを0化する |
| UD-044 | bootstrap/section/history-atはSQLiteの単一read transactionと1つのserver demo時刻でスナップショットを作る。`stateVersion` ETagで再検証し、動的結果の固定TTLは0。SSEで更新通知し、切断時は5秒pollへフォールバックする |

## 11. エンティティ見直し

従来案へ次を反映する。

- `DemoScenario`を動的履歴のルートにし、`WallState`、`Artwork`、`WallRevision`、`PublicationAttempt`が必ず`scenarioId`を持つ。
- `ActiveScenario`を1行だけ持ち、リセットは履歴書換えではなくポインタの原子切替とする。
- `PublicationAttempt`を追加し、冪等性、処理中、失敗再送をArtworkから分離する。
- `DemoSession`はブラウザ識別でありscenario外に置く。Artworkへ表示名snapshotを保存する。
- server生成の退色画像は派生キャッシュであり履歴エンティティにしない。cache keyは`artworkHash|baseHash|pPermille|rendererVersion`。
- 静的`Wall`と動的`WallState`を分離し、原典CityGML・GLBを更新しない。

## 13. 実装開始条件

設計判断の未確定事項はない。実装開始後に必要なのは次の合否確認である。

1. `BV-001`: 東京タワー周辺LOD3 CityGMLからAppearanceと元IDを保った描画可能壁面を12面抽出できる。
2. `BV-002`～`BV-004`: 1壁面の2D/3D往復、外観忠実度、2mm offsetが合格する。
3. `UD-029`～`UD-031`: 退色、描画性能、12壁レイアウトの実測が合格する。
4. いずれかが不合格なら、要件を暗黙変更せず、代替方式と工数差を本書へ追記してから切り替える。
